# Componenta Composer Plugin

Генерирует PHP-файл с упорядоченным списком имён классов провайдеров конфигурации, объявленных в пакетах Composer. Требуются PHP 8.4+ и Composer Plugin API 2.6+.

## Установка

Устанавливайте плагин как рабочую зависимость приложения, а не как зависимость только для разработки или в переиспользуемые библиотеки:

```bash
composer require componenta/composer-plugin
```

Разрешите выполнение плагина в конфигурации Composer корневого проекта:

```json
{
  "config": {
    "allow-plugins": {
      "componenta/composer-plugin": true
    }
  }
}
```

## Метаданные пакета

Пакеты объявляют провайдеры в своём `composer.json`:

```json
{
  "extra": {
    "componenta": {
      "config-providers": [
        "Componenta\\Http\\Router\\ConfigProvider"
      ]
    }
  }
}
```

Корневой пакет может объявлять провайдеры таким же способом. Если провайдеров нет, ключ можно опустить или указать пустой список. При наличии `extra.componenta` должен быть объектом, а `config-providers` — списком непустых имён классов. Значения null, некорректные идентификаторы и зарезервированные имена классов отклоняются. Имена содержат разделители пространств имён без начального разделителя. Плагин не загружает классы и не создаёт их экземпляры.

Только корневой проект определяет путь к генерируемому файлу:

```json
{
  "extra": {
    "componenta": {
      "config-providers-file": "config/componenta-providers.php"
    }
  }
}
```

По умолчанию используется `config/componenta-providers.php`. Относительные пути разрешаются относительно директории проекта (расположения composer.json, используемого командой Composer, даже если это символическая ссылка); абсолютные локальные пути поддерживаются. Явно заданный некорректный путь или null отклоняется. Глобально установленный плагин не генерирует файл в посторонних проектах, если проект не указал путь явно и не требует или не содержит локально установленный плагин.

## Порядок и генерируемый файл

Пакеты с провайдерами следуют после своих установленных зависимостей, в том числе транзитивных зависимостей через пакеты без провайдеров. При разрешении требований учитываются алиасы версий, в том числе альтернативные требования self.version, преобразованные алиасом. Отсутствующие в памяти алиасы восстанавливаются из сгенерированных метаданных installed.php только для установленных пакетов с совпадающими версиями и идентификаторами ревизий; файл блокировки не расширяет установленный набор. Установленный пакет с совпадающим именем и подходящей версией имеет приоритет над виртуальными поставщиками и заменяющими пакетами. Если прямого совпадения нет, учитываются все установленные подходящие поставщики и заменяющие пакеты: Composer не сохраняет единственного выбранного поставщика для неоднозначного виртуального требования. Самостоятельное удовлетворение собственного требования не создаёт ребра графа. Требования к платформе Composer (PHP, расширения, системные библиотеки и API Composer) не образуют зависимостей между провайдерами, даже если установленные пакеты объявляют их поддержку. Такие требования может удовлетворять сама платформа, а порядок провайдеров не должен зависеть от окружения PHP, в котором запущен Composer. Если нужен провайдер конкретного пакета, объявите зависимость непосредственно от этого пакета.

Среди пакетов, зависимости которых уже выведены, приоритет имеет корневой проект, затем установленные пакеты в лексикографическом порядке имён. Это исключает зависимость результата от порядка установки и сериализации installed.json. Самостоятельный сортировщик ProviderPackageSorter сохраняет исходный порядок входных данных в качестве критерия разрешения равенства. Циклы между несколькими пакетами с провайдерами отклоняются. Цикл только между пакетами без провайдеров или с единственным пакетом с провайдером сам по себе не препятствует упорядочиванию. Сортировщик отклоняет дублирующиеся записи пакетов. Повторяющиеся имена провайдеров выводятся один раз без учёта регистра ASCII с сохранением первого написания. Порядок классов внутри пакета сохраняется.

Сгенерированный файл возвращает упорядоченный список строк:

```php
<?php

declare(strict_types=1);

return [
    'Componenta\\App\\ConfigProvider',
    'Componenta\\Router\\ConfigProvider',
];
```

Список используется приложением; в Componenta App за его загрузку отвечает `Componenta\App\Config\ComposerPackageConfigProvider`. Плагин не загружает конфигурацию, не создаёт контейнер и не собирает приложение.

## Жизненный цикл Composer

Генерация выполняется на событиях `post-autoload-dump`, `post-install-cmd` и `post-update-cmd`. Используется набор установленных пакетов, а не только файл блокировки, с учётом режима разработки из события. При `--no-dev` исключаются пакеты, установленные только для разработки, в соответствии с метаданными Composer (или его алгоритмом достижимости, если список таких пакетов пуст). Требования корневого пакета из require-dev влияют на порядок только в режиме разработки.

Команды `composer dump-autoload --no-dev` и `composer dump-autoload --dev` обновляют список. Установка или обновление с `--no-autoloader` также обновляет список; перед запуском приложения необходимо обеспечить соответствующий автозагрузчик. При обновлении только файла блокировки и при загрузке пакетов без установки существующий список не изменяется. Команды, отключающие плагины или сценарии, могут пропустить генерацию. Перед запуском приложения выполните `composer dump-autoload` с включёнными плагинами и сценариями.

Неизменившееся содержимое не перезаписывается. Изменившееся содержимое полностью записывается во временный файл в целевой директории, после чего файл заменяется переименованием. Сохраняются существующие биты прав доступа; для нового файла используются права 0666 с учётом маски процесса. Сохранение владельца и расширенных списков контроля доступа не гарантируется. Символические ссылки и нерегулярные целевые файлы отклоняются. Инвалидация OPcache выполняется только для текущего окружения PHP; рабочие процессы могут требовать перезапуска.

Файл является генерируемым артефактом сборки. Исключите его из системы контроля версий и обеспечьте генерацию до запуска приложения. Не редактируйте его вручную. При деактивации или удалении плагина файл не удаляется автоматически, поскольку путь задаётся приложением и файл может принадлежать пользователю. При удалении интеграции явно удалите устаревший файл. Ошибки генерации приводят к завершению команды Composer с ошибкой; при неудачной временной записи предыдущий файл намеренно не перезаписывается.

## Публичный API

- `ComponentaPlugin` — точка входа плагина и подписчик на события Composer. При ручном вызове `generateProviders()` без события используется установленный набор пакетов.
- `ProviderPackage` — неизменяемое имя пакета и его дополнительные метаданные.
- `ProviderExtractor::extract()` — проверка и получение объявленных имён провайдеров.
- `ProviderCollector::collect()` — сбор имён провайдеров в исходном порядке с устранением повторов.
- `ProviderPackageSorter::sort()` — упорядочивание пакетов с провайдерами по явно заданным зависимостям между именами пакетов.
- `ProviderFileRenderer::render()` — проверка и формирование PHP-кода со списком имён провайдеров.
- `ProviderFileWriter::write()` — обновление целевого файла; возвращает признак изменения его содержимого.

Остальные классы являются внутренними деталями реализации.

## Разработка

```bash
composer install
composer test
composer test:integration
```

Интеграционный тест запускает Composer во временном проекте с локальными репозиториями пакетов. Проверяются установка, переключение режима автозагрузки, переход с версии 1.0.3, обновление плагина и установка без генерации автозагрузчика. После установки зависимостей разработки загрузка внешних пакетов не требуется.

Связанные пакеты: [Componenta App](https://github.com/componenta/app), [Componenta Config](https://github.com/componenta/config), [Componenta Skeleton](https://github.com/componenta/skeleton).
